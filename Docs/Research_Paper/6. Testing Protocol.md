6. Testing Protocol

### 6.1 Test Objectives
The testing protocol verifies:
1. Dataset integrity and split consistency
2. Convergence behavior of the 70-epoch run
3. Final model detection quality on validation and held-out test data
4. Class-wise strengths and failure points
5. Export readiness for deployment workflows

### 6.2 Metrics Used
1. Precision: fraction of predicted positives that are correct
2. Recall: fraction of ground-truth instances that are detected
3. mAP@50: mean AP at IoU threshold 0.50
4. mAP@50-95: mean AP across IoU thresholds from 0.50 to 0.95

These metrics are standard for object detection benchmarking and are generated by the Ultralytics validation pipeline (Ultralytics, 2026a).

### 6.3 Test Environment
1. Model under test: models/runs/moskita_v1210/weights/best.pt
2. Dataset config: data/annotated/data.yaml
3. Runtime: Python 3.12.3, Ultralytics 8.4.38, PyTorch 2.10.0+cu128
4. Device: NVIDIA RTX 2060 Mobile (primary), CPU fallback only if needed

### 6.4 Step-by-Step Testing Procedure
1. Verify data paths and class-name mapping in data.yaml.
2. Count image files, label files, and total annotation instances by split.
3. Confirm training run completeness from results.csv row count and last epoch presence.
4. Re-run validation using the selected checkpoint on split=val.
5. Re-run held-out testing using the same checkpoint on split=test.
6. Record aggregate metrics (P, R, mAP@50, mAP@50-95).
7. Extract class-wise precision, recall, AP50, and AP50-95 for test split.
8. Inspect training curves and confusion matrix figures.
9. Verify ONNX export file existence and non-zero file size.

### 6.5 Protocol Matrix
| Test ID | Purpose | Method | Acceptance Criterion | Result |
|---|---|---|---|---|
| TP-01 | Data integrity | Count image/label files and instances per split | No missing split folders, consistent label presence | Pass |
| TP-02 | Training completeness | Inspect results.csv for 70 rows and final epoch record | Exactly 70 epochs recorded | Pass |
| TP-03 | Validation performance | Run model.val split=val on best.pt | mAP@50 >= 0.75 target | Pass (0.9102) |
| TP-04 | Held-out generalization | Run model.val split=test on best.pt | mAP@50 >= 0.75 target | Pass (0.9340) |
| TP-05 | Class behavior analysis | Extract per-class metrics from test run | Report top and weak classes with support counts | Pass |
| TP-06 | Export integrity | Check ONNX files in models/exports | Export exists and file size > 0 | Pass |

### 6.6 Interpretation Rules
1. Aggregate performance is considered strong when mAP@50 exceeds 0.85.
2. Low-support classes are interpreted cautiously due to high statistical variance.
3. Differences between mAP@50 and mAP@50-95 are used to assess localization strictness sensitivity.
4. Any high aggregate metric is validated against per-class metrics to avoid majority-class bias.

### 6.7 Known Test Limitations
1. Class imbalance remains present in the assembled dataset.
2. Some classes have very low support in test split (for example basin and styrofoam_container), reducing confidence in class-level stability.
3. End-to-end Raspberry Pi 5 runtime benchmarking is outside this report's measured protocol and should be added in deployment validation.
